# Design

## Context

См. `proposal.md` о мотивации. `RewardService.request` создаёт заявку отдельно от резервирования. `reserve_atomic` пишет сумму в `user_bonus` с `event_id` заявки. В `UserReward` суммы нет. Подтверждение берёт текущую цену каталога, проверяет общий резерв вне записи и выполняет batch. Карточки `new` отображаются в `ui/admin/tabs/requests.py`, остальные заявки уже попадают в историю.

Изменение пересекает модель, репозиторий, сервис и UI и затрагивает конкурентные изменения финансовых данных, поэтому требует этого дизайна.

## Goals / Non-Goals

**Goals:** единая граница фиксации решения, возврата и журнала; совместимость существующих заявок без массовой миграции; проверяемая защита от повторов и конкуренции.

**Non-Goals:** исправление всего процесса создания заказа, массовая отмена, отмена `completed`, добавление уведомлений об отмене и переработка остальных операций начисления.

## Decisions

### Транзакция решения в BonusLedgerRepo

Добавить отмену через Firestore transaction в `bonus_ledger_repo.py`. Внутри прочитать заявку и пользователя, проверить `new`, владельца, сумму и достаточный резерв; все чтения выполнить до записей. Одним commit обновить оба поля баланса, статус `cancelled`, дату решения и создать запись `TransactionType.REFUND = "refund bonus"` с `EventType.USER_REWARD`. Владельца брать из заявки, не из параметров UI. Ошибки преобразовывать в доменный результат/ошибку, различая уже решённую заявку и ошибку хранения.

Альтернатива batch атомарно записывает изменения, но не защищает условие `new` от конкуренции. Проверка статуса в сервисе тоже недостаточна. Firestore transaction повторяет чтения при конфликте; при повторе завершённая заявка не изменяется. Побочные эффекты, включая UI и уведомления, не выполняются внутри повторяемого callback.

### Подтверждение использует ту же границу решения

Перевести `settle_reserved_atomic` на транзакционную проверку статуса и баланса, читая те же документы. Использовать исходную сумму заказа, а не текущую цену каталога. Конкурирующие подтверждение и отмена конфликтуют на документе заявки; разные заявки одного пользователя согласуются через документ пользователя. Повторное подтверждение не создаёт новый debit. Существующее уведомление об успешном подтверждении вызывается после commit; его ошибка не отменяет зафиксированное решение.

### Журнал резервирования как источник суммы

Для всех заявок читать внутри транзакции записи `user_bonus`, связанные с ID заявки через `event_id` и тип `reserve bonus`. Требовать ровно одну запись с совпадающими владельцем и `event_type = user_reward`, положительной целой суммой `bonus_value`. Не фильтровать несовпадающего владельца так, чтобы скрыть повреждённые данные. Общий резерв должен покрывать сумму. При отсутствии, неоднозначности или некорректности резервирования прекратить операцию без записей.

ID карточки берётся из ID документа `user_reward` через `UserReward.id`. При резервировании тот же ID передаётся как `user_bonus.event_id`. ID самого документа `user_bonus` — отдельный идентификатор транзакции, и его равенство ID заявки не требуется. В снимке `firestore-backup-m8-agency-20260921T185249Z.json` у всех 35 заявок найдено ровно одно связанное резервирование с совпадающим владельцем. Это подтверждает снимок, но не заменяет проверки данных при выполнении операции.

Поле `reserved_bonus_amount` не добавляется; формат создания заявки и резервирования сохраняется. Если создание заявки прошло, а резервирование завершилось ошибкой, отсутствие связанной записи блокирует возврат. Каталог и переданную UI сумму не использовать. Ручное восстановление повреждённых данных вне этого изменения.

Альтернатива сохранять сумму в заявке дублирует существующий журнал; цена каталога может измениться после заказа. Единый источник в журнале работает для существующих и новых заявок без миграции. Проверить индекс запроса резервирований и включить его конфигурацию, если необходим.

### Проверка на тестовой базе

При разработке подключиться к тестовой базе и проверить связь ID заявки с `event_id` резервирования. Изменяющие проверки выполнять на специально созданных тестовых пользователях и заявках: одиночная отмена, две заявки одного пользователя, повторная отмена и одновременное подтверждение с отменой. Сверять статус, оба баланса, сумму и число связанных записей журнала до и после операции. Зафиксировать результаты без публикации ключей и персональных данных. Проверки сбоев и воспроизводимые конкурентные сценарии также выполнить на эмуляторе без production credentials. При недоступности тестовой базы явно зафиксировать невыполненную проверку, не подменяя её результатами эмулятора.

### UI и права

Добавить вторую кнопку отправки в существующую форму карточки, с отдельным callback отмены по `user_reward_id`. Использовать административный маршрут и существующую проверку роли; обычному пользователю действие не предоставлять. После commit обновить список запросов и данные баланса в сессии, если они закешированы. Ошибка не должна скрывать карточку; конфликт решения требует обновления списка и сообщения, что заявка уже обработана. Показывать отмену в истории администратора и пользователя понятным русским статусом. Не удалять документ заявки.

## Risks / Trade-offs

- Старые заявки без корректного резервирования → отказ без изменения денег и понятная ошибка; не угадывать сумму.
- Повтор callback транзакции → только чтения и записи Firestore внутри callback, никакой отправки сообщений.
- Недостаток общего резерва вследствие старых ошибок → отказ без отрицательного баланса.
- Mock-тесты сами по себе не доказывают поведение Firestore при конкуренции → дополнить сценариями транзакционных конфликтов на эмуляторе без production credentials.
- У старого кода подтверждения нет защиты от гонки → выкатывать отмену и обновлённое подтверждение вместе, остановив старые экземпляры перед доступностью отмены.

## Migration Plan

Добавить enum без изменения старых значений; развернуть совместимые UI, сервис и репозиторий вместе. Прогнать focused tests, Ruff, mypy и pytest. Проверить конкуренцию на эмуляторе и согласованные сценарии на тестовой базе. Обязательной миграции данных нет. При откате отключить действия решения либо вернуть версию с сохранённой защитой транзакций: старое подтверждение небезопасно для уже отменённых заявок в устаревшей сессии. Сохранить журнал возвратов и отменённые заявки при любом откате.
